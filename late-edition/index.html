01 WHAT THIS IS

A translation · not a re-design

Your methodology splits architectural commitments into three bands (strong / medium / fuzzy), routes pre-architecture thinking into discussion/, and demands an ICD on every boundary that crosses a code session. This supplement re-reads the design doc and rival AI spec through that lens, names the ICDs to author before code starts, and proposes a band-labeled roadmap with explicit re-evaluation slots.

Band legend: strong load-bearing for next 3 milestones medium directional for milestones 4–7 fuzzy sketch beyond the horizon discussion pre-architecture · not a commitment re-eval paper session · no code

The horizon for Late Edition: N = 3 milestones, M = 7 — small-team / high-cadence defaults from your methodology. Re-eval cadence: every 3 milestones, plus before every band-tier transition.

“The design doc is what you want. Phase 0 is what you commit to building first.” — working principle

03 ICDS — INTERFACE CONTRACTS

Six contracts to author before any code session opens · cheapest artifact in the pipeline

Each of these crosses a code-session boundary. Each one must exist before the first code session that touches it. Sketch shapes below — each gets its own file (icds/ICD-XX.md) before milestone 0.1.

ICD-01 · World ↔ Renderer

Per-frame contract

What the simulation hands the renderer each frame. Keeps simulation pure; keeps renderer dumb.

// Per frame
interface WorldFrame {
  cameraTarget: Vec3;
  buildings: BuildingView[];   // pos, kind, hp, tier
  units:     UnitView[];       // pos, facing, kind, state
  leads:     LeadView[];       // pos, tier, age
  rain:      RainConfig;       // intensity 0-1
  fog:       { near, far, color };
  hud:       HudState;         // edition, deadline_ms, resources
  effects:   FxEvent[];        // flashes, prints, deaths
}

ICD-03 · Unit ↔ Pathfinder

A* over precomputed grid

Single request shape across all unit kinds. Grid baked at city-gen time; per-building recompute on placement.

interface PathRequest  { from: GridCell, to: GridCell, unitKind: UnitKind }
interface PathResponse {
  found: boolean;
  cells: GridCell[];          // empty if !found
  cost:  number;
  recomputeOn: BuildingId[];  // invalidation set
}

}

ICD-06 · Edition / Print Cycle Events

The clock event contract

The print cycle is the heartbeat — everything subscribes to it. Strong-band by virtue of touching every subsystem.

type CycleEvent =
  | { kind: 'CYCLE_TICK', dt_ms }
  | { kind: 'DEADLINE_WARNING', remaining_ms: 30_000 }
  | { kind: 'DEADLINE_FIRE', edition: number }
  | { kind: 'EDITION_DEBRIEF_BEGIN', edition: number, summary: EditionSummary }
  | { kind: 'EDITION_DEBRIEF_END' }
  | { kind: 'CYCLE_BEGIN', edition: number };
Caller-triggered note. ICD-02 commits to the full Intent vocabulary even though the vertical slice only implements RAID_BUREAU and PASS for the Evening Star. The other intents ship as no-ops with the trigger named (specific later milestones). This is the caller-triggered pattern from your methodology §Phase 2 — the contract is decidable now, the bodies fill in as their callers arrive.

05 PAPER SESSIONS — INSIDE CODE OR OUTSIDE

Which TBDs Claude Code can settle on paper vs which deserve design mode

Your methodology is explicit that architecture sessions and code sessions are different sessions — but it doesn't say architecture sessions must happen outside the code IDE. They must happen before code-writing, and produce written outputs. A “paper session” inside Claude Code is fine for items where the design space is small and the consequences are local.

Settle inside Claude Code (paper session)

  • ICDs 01–06. The shapes are 90% drafted above. A focused arch session in Code can finalize them.
  • Save schema migrations. Mechanical — version field + a switch on version. Settle when ICD-04 is authored.
  • Tutorial first-edition script. Diegetic flow (“your old man left notes”). Beat sheet only; final copy can be a code session.
  • Difficulty selector deferral note. Just a one-page discussion/ file saying “post-MVP, frequency-scaling only.”
  • Yellow/Establishment branch heuristic. One line of math; settle when Tier-1 approaches.
  • Accessibility first pass. Checklist + non-visual deadline cue (audio sting + HUD shake at T-30s).
  • Audio asset manifest. done — see Supplement C. 6 ambient beds + 6 music stems + 24 SFX + 60 VO lines as Venice-ready prompts.

Come back to me (design mode)

  • HUD corkboard interactive mock. The design beat is visual — pinned dossiers, deadline ticker, debrief animation. Worth a hi-fi pass before milestone 0.9.
  • Authored arc writing. The 8 arcs need a writer's voice. Headlines, branches, dialogue. Not a code-session output.
  • Rival AI behavior trees v2. After playtest reveals where the v1 spec broke down. Re-design pass, not a tightening.
  • Tech tree branch endings. The Yellow vs Establishment endings are narrative + UI moments — design mode.
  • Procedural city generation rules. Future feature; design when MP architecture stabilizes.
  • Touch polish. If/when tablet becomes a real target, the HUD wants a focused redesign session.
Rule of thumb. If the question can be answered with text and a table, it's a paper session inside Claude Code. If the question wants visual exploration, a UI mock, or multiple design variants compared side-by-side, come back to design mode.

06 WHAT TO DO MONDAY

Concrete order of operations · architect first · code second
  1. Spin up a fresh code project. Drop in: the design doc, supplement A (rival AI spec), this supplement, and the methodology MD as METHODOLOGY.md.
  2. Create architecture/, icds/, discussion/, deferred/. Empty directories matter — they signal the methodology to the next session.
  3. Open an architecture session (paper-only) with the design doc as context. Author icds/ICD-01.md through ICD-03.md + ICD-05.md + ICD-06.md using the sketches above as starting points. Save schema (ICD-04) waits until PRE-0.8.
  4. Seed the discussion/ tree with the six files named in §02. Each one is a paragraph; they're parking spots, not commitments.
  5. Write architecture/00-overview.md with the strong/medium/fuzzy section list from §02 above. Section headers carry their band; unlabeled is strong.
  6. Write roadmap.md from §04 above, verbatim. Re-eval slots are first-class entries.
  7. Open a code session against milestone 0.1. Read the docs first. Lift the feel-test code as the starting renderer. Land within one session.
  8. Test, merge, write back any deviation into the affected ICD in the same PR. Constraint #4 of the methodology.
  9. Repeat through 0.3. Then the first re-eval. Then keep going.

If a code session opens without an ICD it needs, stop and run an architecture session. That's the methodology working as designed, not a delay.
